# Milestone 3 implementation plan

> Execute the user's approved Milestone 3 scope with focused implementation and independent review. Existing design brief: `landlord-repair-assistant-build-plan.md`, Data contract and Milestone 3. No Milestone 4 work.

**Goal:** Save editable drafts and approve exactly the saved revision reviewed by the landlord, once.

**Architecture:** React keeps unsaved form edits separate from the last saved draft. FastAPI owns draft IDs, revisions, checks, and statuses. SQLite stores current drafts, immutable revision snapshots, and one immutable work order per draft. Approval validates and inserts atomically. Existing read checks remain available.

**Stack:** Existing React/TypeScript/Vite/Tailwind and Python/FastAPI/SQLite. No added integration or model dependencies.

## Binding contract

- Keep all current RepairDraft business fields; add `review_reasons: string[]` (default empty). `preferred_date` remains the API name, but UI label is **Requested date**. Date is optional and never a booking. No sending messages. Microphone stays **Voice not connected**.
- Editable fields: property_id, unit_id, issue_summary, category, contractor_id, preferred_date, access_notes, contractor_message. Backend rejects user-supplied revision, ID, evidence, status, or review results inside fields.
- `POST /api/drafts`: `{session_id, fields}` → RepairDraft. Omitted/null contractor_message generates a simple grounded draft message once. Empty string is preserved as missing information. At most one active draft per session. A retry with matching editable fields returns the existing draft; differing fields when an active draft exists returns 409 `active_draft_exists` with that draft, never silently overwrites it. A terminal draft permits a new workflow/draft.
- `PATCH /api/drafts/{id}`: `{session_id, expected_revision, fields}` → RepairDraft. Fields are partial; omitted fields remain unchanged. Require exact current revision and editable status. Keep ID; increment revision for an actual edit, persist revision history. Preserve user-entered strings exactly; optional empty date may normalize to null. Recompute evidence, missing fields, review reasons, and status using real records. Do not regenerate an edited contractor message on later saves.
- `POST /api/drafts/{id}/approve`: `{session_id, expected_revision, idempotency_key}` → WorkOrder. Require ownership and exact reviewed revision. Revalidate required fields, property/unit relationship, supported category, contractor trade/property approval, safety, and current duplicates under the write transaction. WorkOrder.snapshot is the exact saved reviewed RepairDraft, including its revision, strings and evidence; approving changes the current draft status to approved without changing its content revision. No message sending. Insert a matching approved jobs record for subsequent duplicate checks.
- `POST /api/drafts/{id}/cancel`: `{session_id, expected_revision}` → cancelled RepairDraft. Reject stale/approved drafts; cancellation cannot lead to approval. Repeated cancellation of the returned revision can return the cancelled draft. Record cancellation in history.
- `GET /api/work-orders`: WorkOrder[] for the single demo landlord. `GET /api/sessions/{id}` now returns its latest draft (terminal or active), existing catalog/activity/jobs. Read-check route still makes no draft/order writes.
- Errors from new routes: HTTP 409 for conflicts (`stale_revision`, `draft_cancelled`, `draft_approved`, `active_draft_exists`, `idempotency_conflict`, `approval_blocked`), 404 for unknown IDs; JSON `{error_code, message, draft?, missing_fields?, review_reasons?}`. Existing M2 error handling stays valid.
- Approval retries for same draft/revision return the original WorkOrder even with a different retry key. Stale revisions still fail. Reusing a key for a different draft/revision conflicts. A UNIQUE draft_id constraint and BEGIN IMMEDIATE transaction prevent parallel duplicates. Two drafts for the same issue also cannot create two jobs: the second sees the first approved job during revalidation.
- Additive SQLite schema migration on existing DB. Preserve every fixture and existing session. No database reset or reseed. Test DBs must be temporary.
- Frontend uses explicit Save draft / Save changes. Approve only when persisted, clean, ready, and not busy; never auto-save inside approval. Stable idempotency key per draft/revision. Store session ID in localStorage to resume after reload, fetch authoritative data. Clear cancelled/approved workflow only on explicit New request. Keep unsaved edits on errors and show conflicts clearly; require loading/reviewing latest server draft, never silently retry approval with a new revision.
- Preserve working checks: Load example uses actual /repair-check. A checked local card can be saved as a draft. Once an active saved draft is open, avoid replacing it with a different example; require finishing/cancelling it first. Card edits recheck on Save changes. Clearly show unsaved vs saved revision and disabled approval reasons.
- Display saved orders with expandable exact details/message after reload. Avoid duplicate entries between jobs and orders. No hardcoded business results.

## Review focus

Unsaved edits must never be approved; older tabs must not overwrite current content; a failed approval response must be safe to retry; unrelated date/notes/message edits must not be regenerated or lost; revoked contractor approval or a newly created duplicate must block approval; backend restart must preserve records and revision history.
